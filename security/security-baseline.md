# Security Baseline — Видеочат-комната (`video-chat-room`)

| | |
|---|---|
| **Документ** | Security Baseline / Threat Model (продуктовый) |
| **Версия** | 1.0 |
| **Основан на** | `prds/video-chat-room/prd-video-chat-room.md` (PRD v1.0) |
| **Режим генерации** | `/threat-model` (разово, до `/design`) |
| **Область** | Веб-приложение группового видеозвонка: React-клиент + Node.js/Socket.io сигналинг + WebRTC mesh (до 4 участников), публичный Google STUN, состояние в памяти сервера, без БД, без authN/authZ |

> Этот документ — **источник правды по безопасности** для фичи. Каждый TDD (раздел 10) и каждый PR обязаны свериться с **чек-листом (§7)**. Аудит перед мержем (`/security-audit`) проверяет реализацию именно по §7 и §10 TDD.
>
> Ключевой контекст архитектуры (PRD §7): медиа идёт **P2P** между браузерами и шифруется штатным **DTLS-SRTP** — сервер медиапотоки **не видит**. Сервер видит и ретранслирует **сигналинг** (SDP/ICE), **чат** и **системные события**. Всё состояние — **эфемерное, в памяти**, удаляется при выходе последнего участника.

## 1. Активы и границы доверия

### 1.1 Активы (что защищаем)

| ID | Актив | Где живёт | Чувствительность | Заметки |
|----|-------|-----------|------------------|---------|
| A-1 | **Медиапотоки** (видео/аудио участников) | P2P между браузерами | Высокая (PII: лицо, голос, фон) | Шифруются DTLS-SRTP; сервер к ним доступа не имеет |
| A-2 | **Сигнальные сообщения** (SDP-офферы/ответы, ICE-кандидаты) | Клиент ↔ сервер ↔ клиент (Socket.io) | Средняя | Раскрывают локальные/публичные IP, кодеки, топологию сети |
| A-3 | **Сообщения чата** (имя + текст + время) | Клиент ↔ сервер ↔ клиенты; история — в памяти сервера | Средняя (может содержать ссылки, персональные данные, вводимые пользователем) | Сервер видит открытым текстом; хранится только на время жизни комнаты |
| A-4 | **Отображаемое имя участника** | Вводится клиентом, ретранслируется всем | Низкая/Средняя | Вектор XSS и спуфинга; отображается в чате и оверлеях видео |
| A-5 | **Идентификатор комнаты (room-id)** | URL + память сервера | Средняя (это де-факто «пароль» комнаты — единственный барьер входа) | Угадываемость room-id = несанкционированный вход (принятый риск, см. §2) |
| A-6 | **Внутренний идентификатор участника** | Генерируется сервером (socket-id/UUID), в UI не показывается | Низкая | Используется для маршрутизации и различения одинаковых имён |
| A-7 | **In-memory состояние сервера** (карта комнат, участников, счётчиков, история чата) | RAM Node.js процесса | Высокая (доступность сервиса) | Не персистентно; главная мишень для DoS через переполнение памяти |
| A-8 | **Доступность сигнального сервера** | Node.js процесс | Высокая | Без сервера невозможны вход, чат и установка новых P2P-соединений |

> **Секретов приложения почти нет:** нет БД-паролей, нет прикладных токенов, нет TURN-креденшелов (TURN вне объёма — PRD §5). Единственный «секрет-подобный» актив — room-id (A-5), и он намеренно слабый (см. §2). Это упрощает модель: утечка секретов из кода/логов — низкий риск, но всё равно контролируется (§7 п. 15).

### 1.2 Границы доверия

```
                    ┌───────────────────────────────────────────┐
                    │        Браузер-клиент (НЕДОВЕРЕННЫЙ)        │
                    │  React UF · getUserMedia · RTCPeerConn      │
                    └───────────────────────────────────────────┘
     Граница TB-1        │ WSS (Socket.io)          │ DTLS-SRTP (P2P)
   клиент ↔ сервер       ▼                          │  Граница TB-3
                ┌──────────────────────┐            │  пир ↔ пир
                │  Node.js + Socket.io │            │  (недоверенный SDP/ICE)
                │  сигналинг · чат ·   │            ▼
                │  лимит · in-memory   │     ┌──────────────┐
                └──────────────────────┘     │ Другой пир   │
                    │ Граница TB-2            └──────────────┘
                    ▼ сервер ↔ внешний STUN
              ┌──────────────────┐
              │ Google STUN      │  (внешняя, неконтролируемая точка)
              │ stun.l.google... │
              └──────────────────┘
```

- **TB-1 — Клиент ↔ Сигнальный сервер (WSS).** Главная граница валидации. Всё, что приходит от клиента (имя, room-id, текст чата, SDP/ICE, статусы медиа), — **недоверенный ввод** и подлежит серверной проверке. Клиентские проверки — только UX, не защита.
- **TB-2 — Сервер/клиент ↔ Google STUN.** Внешняя зависимость вне нашего контроля. STUN раскрывает публичный IP (это его функция). Недоступность STUN — деградация, не сбой (PRD F-34).
- **TB-3 — Пир ↔ Пир (медиаплоскость).** SDP/ICE, полученные через сервер, обрабатываются WebRTC-стеком браузера. Контент от другого пира (в т. ч. вредоносно сформированный SDP) — **недоверенный**; полагаемся на устойчивость нативного WebRTC-стека, но не расширяем поверхность собственным парсингом SDP.
- **Внутри одной комнаты доверия между участниками нет.** Любой вошедший (в т. ч. по угаданному room-id) — потенциальный злоумышленник по отношению к остальным (спуфинг имени, XSS через чат, флуд).

## 2. Модель аутентификации и авторизации

**Статус: authN и authZ отсутствуют by design (PRD §5, F-06, §7 «Безопасность»).**

- **Аутентификации нет.** Пользователь не регистрируется и не логинится; вводит только отображаемое имя (A-4), которое ничем не подтверждается. Имя — не идентичность, а ярлык.
- **Авторизации нет.** Доступ к комнате определяется **только знанием room-id** (A-5). Любой URL с валидным room-id открывает или создаёт комнату (F-04, F-05). Вход по угаданному/чужому room-id — **штатное поведение** (US-4, F-06).
- **Ролей нет.** Все участники равны; привилегий модератора/создателя нет (F-32, PRD §5).

### Угрозы, которые это открывает (ПРИНЯТЫЙ РИСК)

| Угроза | Последствие | Статус |
|--------|-------------|--------|
| Вход по **угаданному/перебранному room-id** | Посторонний попадает в активный звонок, слышит/видит участников, читает и пишет в чат | **Принятый риск** (PRD §5, F-06, §7). Смягчается только энтропией room-id — см. §7 п. 14 |
| **Отсутствие приватности комнаты** | Нет «закрытых» комнат, лобби, allow-list | **Принятый риск** (Non-Goal: лобби/waiting-room, PRD §5) |
| **Спуфинг имени** — вход под чужим отображаемым именем | Социальная инженерия внутри комнаты | **Принятый риск** (имена не уникальны и не подтверждаются, F-30). Различение — по внутреннему ID (A-6) на уровне системы, не для пользователя |
| Утечка/пересылка ссылки-приглашения | Доступ получает тот, кому ссылку не давали | **Принятый риск** — модель «зашёл по ссылке» (PRD §1, §7) |

> **Важно для аудита:** перечисленное выше — **осознанные компромиссы из PRD, а не дефекты**. Их НЕ нужно «фиксить» введением авторизации/TURN/E2E — это выход за объём (PRD §5). Задача baseline — **ограничить сопутствующий ущерб**: чтобы отсутствие authZ не превращалось в XSS, захват сервера через DoS или переполнение памяти. Именно на это нацелен чек-лист §7.
>
> **Единственная реальная линия защиты входа — непредсказуемость room-id (§7 п. 14).** Слабый (короткий/последовательный) room-id превращает «принятый риск угадывания» в тривиальный автоматический перебор всех активных комнат — это уже **дефект**, а не принятый риск.

## 3. STRIDE-анализ по границам

Обозначения серьёзности: `critical / high / medium / low`. «ПР» = принятый риск (PRD).

### 3.1 Граница TB-1 — Клиент ↔ Сигнальный сервер (Socket.io / WSS)

| STRIDE | Угроза | Сер. | Контрмера (→ §7) |
|--------|--------|------|-------------------|
| **S** Spoofing | Отправка событий от имени чужого участника; подделка отображаемого имени в payload | medium | Сервер сам проставляет автора сообщения по серверному socket-id (A-6), **не доверяя** имени/ID из payload клиента → §7 п. 3, 6 |
| **S** Spoofing | Вход под чужим room-id | high | **ПР** (§2). Смягчение — энтропия room-id → §7 п. 14 |
| **T** Tampering | Модификация чужих сигнальных/чат-сообщений в транзите | high | WSS/TLS обязателен (шифрование транзита) → §7 п. 12, 13 |
| **T** Tampering | Инъекция HTML/JS в имя или текст (XSS-payload) | **critical** | Серверная санитизация/валидация ввода + экранирование при рендере → §7 п. 1, 2, 4 |
| **R** Repudiation | Нет учётных записей и достоверного аудита действий | low | **ПР** (нет authN). Минимальное серверное логирование событий без PII → §7 п. 16 |
| **I** Info Disclosure | Перехват сигналинга/чата в открытом транспорте | high | WSS/TLS обязателен → §7 п. 12 |
| **I** Info Disclosure | Утечка секретов/PII в логах и сообщениях об ошибках сервера | medium | Логи без содержимого сообщений и секретов; клиенту — обобщённые ошибки → §7 п. 15, 16 |
| **D** DoS | **Флуд сообщениями/событиями** (чат, join, ICE-спам) — рост CPU и памяти | high | Rate limit на сообщения и события; серверный лимит частоты → §7 п. 5 |
| **D** DoS | **Гигантский payload** (имя/сообщение/SDP на мегабайты) — переполнение памяти (A-7) | high | Жёсткие лимиты размера сообщений и максимального фрейма Socket.io → §7 п. 8, 9 |
| **D** DoS | **Массовое создание комнат** случайными room-id — рост карты комнат в памяти | high | Лимит комнат/соединений; очистка пустых комнат; (опц.) cap на число комнат → §7 п. 10, 11 |
| **D** DoS | **Утечка памяти**: комната/история чата не удаляются при выходе последнего | high | Гарантированная атомарная очистка состояния комнаты при падении счётчика до 0 → §7 п. 11 |
| **D** DoS | Раздувание истории чата в долгоживущей комнате | medium | Cap на число/суммарный объём хранимых сообщений комнаты → §7 п. 9 |
| **E** Elevation | Получение прав «модератора»/управление чужими | low | Ролей нет by design (F-32); сервер не реализует привилегированных операций → §7 п. 7 |
| **E** Elevation | **Обход атомарного лимита 4** через гонку одновременных join (US-5) | high | Атомарная серверная проверка+резервирование слота под единой критической секцией → §7 п. 7 |

### 3.2 Граница TB-2 — Сервер/клиент ↔ Google STUN

| STRIDE | Угроза | Сер. | Контрмера (→ §7) |
|--------|--------|------|-------------------|
| **I** Info Disclosure | STUN раскрывает публичный IP участника | medium | **ПР** — это назначение STUN; TURN-релей (скрывающий IP) вне объёма (PRD §5) |
| **D** DoS | Недоступность публичного STUN → часть соединений не устанавливается | medium | **ПР** (F-34): деградация без падения приложения; ICE-config фиксирован, недоступность обрабатывается gracefully → §7 п. 17 |
| **T** Tampering | Подмена ответа STUN (MITM на пути к STUN) | low | Ограничено влиянием на ICE; медиа всё равно защищено DTLS-SRTP (A-1). Использовать штатный публичный STUN-endpoint |

### 3.3 Граница TB-3 — Пир ↔ Пир (медиаплоскость, WebRTC)

| STRIDE | Угроза | Сер. | Контрмера (→ §7) |
|--------|--------|------|-------------------|
| **T** Tampering | Инъекция вредоносно сформированного **SDP/ICE** от пира | medium | Обработка сигналинга только штатным `RTCPeerConnection`; **без собственного парсинга/eval** SDP; отбрасывать некорректные setRemoteDescription/addIceCandidate → §7 п. 18 |
| **I** Info Disclosure | Перехват медиа между пирами | low | Медиа шифруется **DTLS-SRTP** по умолчанию (A-1) — обязательный инвариант WebRTC → §7 п. 12 |
| **S** Spoofing | Пир выдаёт чужой медиапоток/имя | medium | **ПР** (нет authN). Привязка потока к участнику — по серверному socket-id (A-6) |
| **D** DoS | Пир шлёт лавину ICE-кандидатов/renegotiation | medium | Rate limit сигнальных событий на сервере (§7 п. 5); клиент устойчив к некорректному сигналингу (§7 п. 18) |
| **E** Elevation | Выход за пределы браузерной песочницы через медиа-стек | low | Полагаемся на нативный WebRTC-стек браузера; не расширяем поверхность; держим зависимости обновлёнными → §7 п. 19, 20 |

## 4. Защита данных

### 4.1 Транзит
- **HTTPS/WSS обязателен** (PRD §7 «HTTPS обязателен»). `getUserMedia`/WebRTC работают только в secure context; Socket.io обязан использовать WSS. Downgrade на `http://`/`ws://` (кроме `localhost` при разработке) недопустим в проде → §7 п. 12.
- **Медиа (A-1)** — DTLS-SRTP end-to-end между пирами по умолчанию; сервер к плейнтексту медиа доступа не имеет.
- **Сигналинг и чат (A-2, A-3)** — шифруются на уровне TLS до сервера; **на самом сервере видны открытым текстом** (сервер их маршрутизирует). E2E-шифрование чата/сигналинга — Non-Goal (PRD §5).

### 4.2 Хранение (эфемерность)
- **Персистентности нет.** Никакой БД, файлов, localStorage (PRD §5, §7). Всё состояние (A-7) — в RAM Node.js.
- **Жизненный цикл = защита данных:** при выходе последнего участника комната, room-id и **вся история чата удаляются** (F-09, US-10). Это одновременно приватность (данные не залёживаются) и главный инвариант против утечки памяти (§7 п. 11).
- **На клиенте между перезагрузками ничего не сохраняется** (PRD §5) — снижает риск кражи данных с устройства.

### 4.3 Что видит сервер (модель раскрытия)
| Данные | Сервер видит? | Комментарий |
|--------|---------------|-------------|
| Медиа (видео/аудио) | **Нет** | P2P + DTLS-SRTP |
| SDP/ICE (метаданные сети, IP, кодеки) | **Да** | Ретранслирует; логировать НЕ следует (§7 п. 15, 16) |
| Текст чата + имена | **Да** | Хранит в памяти на время жизни комнаты |
| Room-id, состав участников, статусы медиа | **Да** | Оперативное состояние |

### 4.4 PII и логи
- **PII в системе:** лицо/голос (медиа, до сервера не доходит), имя, содержимое чата, IP (в сигналинге). 
- **Логи не должны содержать:** текст сообщений, отображаемые имена, полные SDP/ICE, IP-адреса → §7 п. 16. Логировать допустимо обезличенные события (room-id хешированный/усечённый, тип события, серверный socket-id) для диагностики.
- **Ошибки клиенту** — обобщённые, без стек-трейсов и внутренних деталей → §7 п. 15.

## 5. Риски зависимостей

| Зависимость | Роль | Основные риски | Политика |
|-------------|------|----------------|----------|
| **socket.io** (server+client) | Транспорт сигналинга/чата, WSS | CVE в парсинге фреймов; дефолты, допускающие большие payload; неограниченный размер буфера → DoS памяти | Пинить версию; `maxHttpBufferSize` задать явно (§7 п. 8); отслеживать CVE; регулярный `npm audit` (§7 п. 20) |
| **react** / react-dom | UI-рендер | Небезопасный рендер при `dangerouslySetInnerHTML`; XSS если экранирование обойдено | JSX по умолчанию экранирует — **запрет `dangerouslySetInnerHTML`** для пользовательского контента (§7 п. 4) |
| **WebRTC-стек браузера** | Медиа P2P, DTLS-SRTP, парсинг SDP/ICE | Уязвимости нативного стека; обработка вредоносного SDP от пира | Полагаемся на браузер (не наш код); поддерживаемые версии браузеров (PRD §7); не парсим SDP сами (§7 п. 18) |
| **Google STUN** (`stun.l.google.com`) | ICE/NAT — **внешняя точка** | Недоступность (DoS сторонней инфры); раскрытие IP; смена/отзыв публичного endpoint | **ПР** (F-34). Graceful-деградация (§7 п. 17); ICE-серверы — конфигурируемы, не хардкод в разных местах |
| **Node.js runtime** | Хост сервера | CVE рантайма | Поддерживаемая LTS-версия; обновления безопасности (§7 п. 20) |
| **Транзитивные npm-пакеты** | Сборка/рантайм | Supply-chain, известные CVE | `npm audit` в CI (hygiene); фиксация lock-файла; ревью новых зависимостей (§7 п. 19, 20) |

> Общая политика: **минимум зависимостей**, зафиксированный lock-файл, `npm audit` в CI-гейте `hygiene`, ручное ревью при добавлении новой прод-зависимости, приоритетное обновление при `high`/`critical` CVE.

## 6. Резюме приоритетных рисков

1. **XSS через имя/сообщение чата (critical).** Пользовательский контент отображается в чате и оверлеях у всех участников; без серверной санитизации + экранирования при рендере — исполнение произвольного JS в браузере жертв. Ключевой класс угроз (US-1, US-8, F-38, F-39).
2. **DoS in-memory сервера (high).** Состояние в RAM без БД: флуд событий, гигантские payload, массовое создание комнат, утечка памяти при неудалённых комнатах — прямой путь к падению единственного сервера (A-7).
3. **Гонка за лимит 4 участника (high).** Неатомарная проверка лимита → комната переполняется сверх mesh-предела, деградация качества/устойчивости (US-5, F-05).
4. **Отсутствие приватности комнаты / угадывание room-id (high, частично ПР).** Единственный барьер — энтропия room-id; слабый идентификатор превращает принятый риск в тривиальный перебор.
5. **Обязательность WSS/HTTPS (high).** Без secure context не работает getUserMedia и открывается перехват сигналинга/чата; downgrade недопустим в проде.

## 7. ЧЕК-ЛИСТ ТРЕБОВАНИЙ БЕЗОПАСНОСТИ

> **Нормативная часть.** Каждый TDD (раздел 10) обязан сослаться на релевантные пункты; каждый PR — свериться. Аудит `/security-audit` проверяет реализацию по этому списку. Формат статуса в TDD/PR: `SEC-NN: covered | n/a (обоснование) | accepted-risk (ссылка на PRD)`.

### Валидация ввода и XSS
1. **SEC-01 (critical).** Отображаемое имя валидируется **на сервере**: длина ≤ 30 символов, запрет спецсимволов/управляющих символов (allow-list допустимых), пустое/из одних пробелов — отклоняется. Клиентская проверка — только UX, не замена серверной. *(F-38, US-1)*
2. **SEC-02 (critical).** Текст сообщения чата валидируется **на сервере**: непустой после `trim`, ограничен по длине (см. SEC-08); пустые/пробельные отклоняются. *(F-24, US-8)*
3. **SEC-03 (critical).** Весь пользовательский контент (имя, текст) проходит серверную санитизацию/нейтрализацию перед ретрансляцией и хранением в истории. *(F-38, F-39)*
4. **SEC-04 (critical).** При рендере имён и сообщений в React контент **экранируется** (только текстовые узлы/`{value}`); **запрещён `dangerouslySetInnerHTML`** и любой innerHTML для пользовательских данных — в чате И в оверлеях видео. *(F-39, US-8 «защита от XSS»)*
5. **SEC-05 (high).** Rate limit на исходящие от клиента события (чат-сообщения, join, сигналинг): ограничение частоты на соединение; превышение — троттлинг/отклонение, без падения сервера. *(F-40, защита от флуда/спама)*
6. **SEC-06 (high).** Автор сообщения и внутренний ID участника проставляются **сервером** по доверенному серверному socket-id (A-6); значения автора/ID из клиентского payload **игнорируются** (анти-спуфинг). *(US-1 «различие по внутреннему ID»)*

### Авторизация слотов и целостность комнаты
7. **SEC-07 (high).** Проверка лимита «≤ 4 участника» и резервирование слота выполняются **атомарно** на сервере (единая критическая секция/синхронный участок event-loop), исключая гонку одновременных join; 5-му — отказ «Комната заполнена». Привилегированных операций (модератор) сервер не предоставляет. *(F-05, F-07, F-08, F-32, US-5)*

### Защита памяти сервера (in-memory состояние)
8. **SEC-08 (high).** Заданы **явные лимиты размера**: максимальная длина имени (30), максимальная длина сообщения чата (разумное значение по умолчанию), и явный `maxHttpBufferSize`/лимит фрейма Socket.io для сигнальных и чат-событий. Превышающие payload отклоняются до обработки. *(F-40, защита A-7 от переполнения)*
9. **SEC-09 (medium).** Ограничен объём истории чата на комнату (максимум сообщений и/или суммарный размер) во избежание неограниченного роста памяти в долгоживущей комнате. *(защита A-7)*
10. **SEC-10 (medium).** Ограничение на массовое создание комнат/соединений: разумный потолок числа одновременных комнат и/или соединений с одного источника; поведение при достижении потолка определено (без краша). *(DoS TB-1)*
11. **SEC-11 (high).** Гарантированная **очистка состояния комнаты** (участники, счётчики, история чата, room-id) при падении счётчика участников до нуля — как при явном выходе, так и при disconnect/обрыве; отсутствие «висящих» комнат и утечки памяти. *(F-09, US-10, US-11)*

### Транспорт и данные
12. **SEC-12 (high).** В продакшене обязателен **HTTPS/WSS**; Socket.io работает поверх WSS; downgrade на `http/ws` запрещён (кроме `localhost` в dev). Медиа-плоскость использует штатный **DTLS-SRTP** (инвариант WebRTC — не отключать). *(PRD §7)*
13. **SEC-13 (medium).** **Secure-заголовки** на HTTP-ответах веб-сервера: `Content-Security-Policy` (ограничить источники скриптов/стилей/connect до нужных — self, WSS-endpoint, STUN; запрет inline-скриптов по возможности), `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `X-Frame-Options`/`frame-ancestors` (анти-clickjacking), HSTS. CSP — дополнительный барьер к SEC-04. *(defense-in-depth XSS)*
14. **SEC-14 (high).** **Room-id криптографически непредсказуем**: достаточная энтропия (например, ≥122 бит, UUIDv4/`crypto.randomUUID` или ≥16 случайных символов из CSPRNG), без последовательностей/угадываемых схем. Это единственная техническая защита входа при отсутствии authZ (§2). *(F-02, смягчение ПР входа по room-id)*
15. **SEC-15 (medium).** **CORS/Origin**: Socket.io и HTTP настроены на разрешённый origin(ы) приложения; wildcard `*` в проде не используется. Ошибки клиенту — обобщённые, без стек-трейсов/внутренних деталей. *(TB-1)*
16. **SEC-16 (medium).** **Логи без секретов и PII**: не логировать текст сообщений, имена, полные SDP/ICE, IP-адреса; допускается обезличенная диагностика (тип события, усечённый/хешированный room-id, серверный socket-id). Нет секретов в коде/репозитории. *(§4.4)*

### Устойчивость сигналинга и внешних зависимостей
17. **SEC-17 (medium).** **Graceful-деградация при недоступности STUN** и при неустановленном P2P-соединении: приложение не переходит в нерабочее состояние, ошибка обрабатывается. ICE-конфиг задаётся в одном месте (конфигурируемо). *(F-34, TB-2)*
18. **SEC-18 (medium).** Обработка **недоверенного SDP/ICE** от пиров только штатным `RTCPeerConnection` API; **без собственного парсинга/`eval`/шаблонизации SDP**; некорректные `setRemoteDescription`/`addIceCandidate` перехватываются и не роняют клиент. *(TB-3)*
19. **SEC-19 (low).** Новая прод-зависимость добавляется только после ревью необходимости; минимизация дерева зависимостей; фиксация lock-файла. *(§5)*
20. **SEC-20 (medium).** `npm audit` (или эквивалент) выполняется в CI-гейте `hygiene`; `high`/`critical` уязвимости блокируют мерж или явно принимаются с обоснованием; браузеры/Node — поддерживаемые версии. *(§5)*

### Принятые риски (фиксируем, не «фиксим»)
21. **SEC-21 (accepted).** Отсутствие authN/authZ, приватности комнаты, TURN-релея (скрытия IP), E2E-шифрования сверх DTLS-SRTP и персистентности — **осознанные компромиссы PRD §5/§7**. TDD и PR ссылаются сюда вместо «исправления». Обязанность разработчика — не допустить, чтобы принятый риск усиливал устранимые угрозы (XSS, DoS, слабый room-id).

## 8. Как пользоваться этим документом

- **TDD (`/design`), раздел 10 «Безопасность»:** перечислить релевантные `SEC-NN` со статусом `covered / n/a / accepted-risk` и указать, каким проектным решением закрывается каждый.
- **PR:** в шаблоне отметить соответствие §7; изменения, затрагивающие ввод/сигналинг/чат/зависимости, обязаны сослаться на затронутые `SEC-NN`.
- **`/security-audit` (перед мержем критичного):** аудит по §7 + §10 TDD; находки ранжируются `critical/high/medium/low` с `файл:строка` и ссылкой на нарушенный `SEC-NN`.
