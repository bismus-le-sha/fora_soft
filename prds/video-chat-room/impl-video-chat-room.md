# Implementation Plan — Видеочат-комната (`video-chat-room`)

| | |
|---|---|
| **Документ** | Implementation Plan (IP) |
| **Версия** | 1.0 |
| **Стадия пайплайна** | План (`/plan`) |
| **feature-name** | `video-chat-room` |
| **Источники** | PRD v1.0 (`prd-video-chat-room.md`, F-01..F-40, US-1..US-13) · TDD v1.1 (`design-video-chat-room.md`, §1..§14) · Security-baseline v1.0 (`security-baseline.md`, SEC-01..SEC-21) |

> Каждая задача = один MR/PR в `develop` (ветка `feature/video-chat-room-<task-id>`), 0.25–1 день.
> Критичные задачи `[critical]` разбиты на пару **тесты (`test-author`) → код (`implementer`)** с гейтом
> «ожидание команды пользователя» между ними и обязательным `security-audit` перед мержем.
> Формат ссылок: `_Requirements: <PRD id / SEC id>, Design: <§ TDD>_`.

## Условные обозначения
- `[critical]` — задача уровня «безопасность / целостность данных / ключевой инвариант»; test-first.
- Оценка — в человеко-днях (ч-д).
- «после N» — жёсткая зависимость (нельзя начинать раньше завершения N).

## Область 0 — Скаффолд монорепо и tooling (DevOps)

  - **Критерии приёмки:** `npm install` в корне ставит оба workspace; `npm run dev` поднимает Vite + Node; CI `hygiene`/`lint`/`test`/`audit` зелёные на пустом проекте.
  - **Оценка:** 1.5 ч-д. **Зависимости:** нет (стартовая).

  - **3.2** `domain/RoomRegistry.js`: `getOrCreate/get/delete/count`; cap `ROOMS_MAX` — отказ создания при достижении без краша (SEC-10).

  - **Оценка:** 1.0 ч-д. **Зависимости:** после 2.

## Область 2 — Сервер: критичные модули безопасности

- [ ] **4. [critical] Валидация и санитизация ввода (SEC-01/02/03)**
  - Серверная валидация имени (trim, ≤`NAME_MAX`, allow-list символов, отклонение пустого/управляющих) и текста (непустой после trim, ≤`MESSAGE_MAX`) + санитизация имени и текста до хранения/ретрансляции.
  - **4.1** `test-author`: юнит-тесты `validateName`/`validateText`/`sanitize` — валидные/невалидные кейсы, границы длины, пустое/пробельное, XSS-payload (`<img onerror>`, `<script>`, `javascript:`) нейтрализуется/отклоняется. Тесты падают (red).
  - **4.2** `implementer`: `lib/validate.js` + `lib/sanitize.js` — тесты зелёные, тесты не менять.
  - _Требования: F-38, F-39, US-1, US-8, SEC-01, SEC-02, SEC-03. Design: §4.1, §7.4, §10.1_
  - **Критерии приёмки:** все тесты 4.1 зелёные; покрытие модулей ≥90%; ни один XSS-payload не проходит в «чистом» виде.
  - **Оценка:** тесты 0.5 + код 0.5 = 1.0 ч-д. **Зависимости:** после 2.

- [x] **5. [critical] Rate-limit token-bucket на соединение (SEC-05)**
  - Троттлинг событий по категориям (chat/signal/join) на соединение; превышение → отклонение + `error{rate-limited}`, без падения сервера.
  - [x] **5.1** `test-author`: юнит-тесты `allow(socketId, category)` — burst в пределах лимита проходит, превышение отклоняется, восстановление токенов со временем (fake timers). Red.
  - [x] **5.2** `implementer`: `lib/rateLimit.js`.
  - _Требования: F-40, SEC-05. Design: §4.1, §9.3, §10.1_
  - **Критерии приёмки:** флуд не приводит к росту необрабатываемой нагрузки; лимиты берутся из `config.js`; покрытие ≥90%.
  - **Оценка:** тесты 0.5 + код 0.5 = 1.0 ч-д. **Зависимости:** после 2.

## Область 3 — Сервер: транспорт, безопасность заголовков, каркас хендлеров

- [x] **8. Каркас socket-хендлеров**

Бизнес-логика лимита/чата делегируется в сервисы (заглушки — наполняются задачами 9–14).
  - _Требования: F-40, SEC-05, SEC-15. Design: §4.1, §6.1, §8_
  - **Критерии приёмки:** интеграционный тест: неизвестное/битое событие → `error{bad-payload}` без краша; rate-limit срабатывает на всех категориях.

## Область 4 — Сервер: критичные инварианты комнаты и чата

- [x] **9. [critical] Атомарный join и лимит 4 участника (SEC-07)**
  - `RoomService.join` как единый синхронный участок event-loop: `isFull()`→`add()` без `await`; 5-й → `join:rejected{room-full}`. Хендлер `join`: rate-limit → `validateName` → `sanitize` → атомарный join → `join:ok{selfId,participants,history,iceServers}` инициатору + `participant:joined` + `chat:system{join}` остальным.
  - **9.1** `test-author`: интеграционный тест (socket.io-client против реального `io`): 5 одновременных `join` в комнату из 3 → ровно 4 участника, 1 отказ `room-full`; невалидное имя → `invalid-name`. Red.
  - **9.2** `implementer`: `services/RoomService.join` + `join`-хендлер + broadcast.
  - _Требования: F-01, F-04, F-05, F-07, F-32, US-2, US-4, US-5, SEC-01, SEC-03, SEC-07. Design: §4.1, §6.1, §7.1, §10.2_
  - **Критерии приёмки:** гонка за последний слот не превышает лимит 4; проигравший получает `room-full`; покрытие RoomService.join ≥90%.
  - **Оценка:** тесты 0.5 + код 0.75 = 1.25 ч-д. **Зависимости:** после 4, 8.

- [x] **10. [critical] Очистка состояния комнаты при выходе/обрыве последнего (SEC-11)**
  - Единый путь `RoomService.leave` для явного `leave` и транспортного `disconnect`: `room.remove(id)` → `participant:left{id}` + `chat:system{leave}` остальным; при `room.size()==0` → `RoomRegistry.delete(roomId)` (участники, счётчик, история, room-id стёрты).
  - **10.1** `test-author`: интеграционный тест — вход/выход последнего участника удаляет комнату (нет утечки: `registry.count()`/`get` пусты, история недоступна); обрыв (disconnect) эквивалентен выходу; повторный вход по тому же id создаёт пустую комнату. Red.
  - **10.2** `implementer`: `RoomService.leave` + обработчики `leave`/`disconnect`.
  - _Требования: F-09, F-17, F-18, US-10, US-11, SEC-11. Design: §5.2, §7.3, §10.3_
  - **Критерии приёмки:** после выхода последнего — `registry` не содержит комнату; нет «висящих» комнат; для многих циклов вход/выход `count()` возвращается к 0.
  - **Оценка:** тесты 0.5 + код 0.5 = 1.0 ч-д. **Зависимости:** после 9.

- [x] **11. [critical] Анти-спуфинг авторства + отправка чата (SEC-06)**
  - Хендлер `chat:send`: rate-limit(chat) → `validateText` → `sanitize` → построить `Message{kind:chat, authorId=socket.id, authorName=снимок}` — поля автора/ID из клиентского payload **игнорируются** → push в историю → broadcast `chat:message`.
  - **11.1** `test-author`: интеграционный тест — клиент шлёт `chat:send` с подделанными `authorId`/`authorName` → сервер проставляет свой `socket.id` и настоящее имя; пустой/пробельный текст отклоняется; санитизированный текст в `chat:message`. Red.
  - **11.2** `implementer`: `RoomService.postChat` + `chat:send`-хендлер.
  - _Требования: F-12, F-13, F-24, US-8, SEC-02, SEC-03, SEC-05, SEC-06. Design: §5.1, §6.1, §7.4, §10.1_
  - **Критерии приёмки:** невозможно выдать себя за другого через payload; пустые сообщения не проходят; все сообщения санитизированы.
  - **Оценка:** тесты 0.5 + код 0.75 = 1.25 ч-д. **Зависимости:** после 4, 5, 9.

- [x] **12. [critical] История чата при позднем входе (F-14/F-23)**
  - Поздний участник в `join:ok.history` видит переписку, отправленную до входа (за время жизни комнаты); ring-buffer ограничен `HISTORY_MAX`.
  - **12.1** `test-author`: интеграционный тест — A отправляет N сообщений, затем входит B → `join:ok.history` содержит эти сообщения (в порядке, с авторами/временем); при >`HISTORY_MAX` хранятся последние. Red.
  - **12.2** `implementer`: включение `history` в snapshot `join:ok`; связка с `pushMessage`.
  - _Требования: F-14, US-8, SEC-09. Design: §5.1, §6.2, §11.2_
  - **Критерии приёмки:** поздний вход видит предыдущую переписку; после удаления комнаты история недоступна (связка с задачей 10).
  - **Оценка:** тесты 0.5 + код 0.5 = 1.0 ч-д. **Зависимости:** после 11.

- [x] **13. Обработчик `media:state` и broadcast**
  - Хендлер `media:state`: rate-limit(signal) → обновить `participant.media{audio,video}` → broadcast `media:state{id,audio,video}` остальным.
  - _Требования: F-09, F-16, F-18, US-7, US-12. Design: §6.1, §6.2, §7.2_
  - **Критерии приёмки:** интеграционный тест — смена статуса mic/cam доставляется остальным; статус хранится в участнике и попадает в `join:ok.participants`.
  - **Оценка:** 0.5 ч-д. **Зависимости:** после 9.

- [x] **14. Ретрансляция сигналинга (offer/answer/ice)**
  - Хендлеры `signal:offer/answer/ice`: rate-limit(signal) → проверить, что `to` — участник той же комнаты → relay `{from,sdp|candidate}` только адресату. Сервер **не парсит** SDP.
  - _Требования: F-06, US-6, SEC-18. Design: §4.1, §6.1, §7.1_
  - **Критерии приёмки:** интеграционный тест — offer доставляется только адресату; `to` вне комнаты игнорируется; SDP ретранслируется как непрозрачная строка.
  - **Оценка:** 0.75 ч-д. **Зависимости:** после 9.

- [x] **15. Прод-раздача статики и `/healthz`**
  - Express отдаёт `app/client/dist` с того же origin в проде; `GET /healthz` → `200 {status:'ok', rooms: count()}` без PII.
  - _Требования: SEC-12, SEC-15. Design: §3.2, §12.2, §12.4_
  - **Критерии приёмки:** health-check возвращает число комнат; статика раздаётся; в dev не мешает Vite.
  - **Оценка:** 0.5 ч-д. **Зависимости:** после 6.
