## 1. Продукт и проблема (кратко)

Видеочат-комната — лёгкий групповой видеозвонок в браузере (до 4 участников) с текстовым чатом, без регистрации: зашёл по ссылке → представился → общаешься. Целевой сценарий — быстрый созвон «лицом к лицу» для небольшой группы (команда, друзья, интервью), без тяжёлых сервисов и настройки.

**Задача дизайна.** Сделать так, чтобы простой по функциям продукт ощущался **продуманным и статусным**, а не «сырым MVP» — за счёт визуальной аккуратности и деталей, а не за счёт добавления функций.

---

## 2. Цели дизайна

1. Первое впечатление и путь «ссылка → в комнате за секунды» должны ощущаться **мгновенными и лёгкими**, без визуального трения.
2. Управление медиа (микрофон/камера) и статус других участников должны считываться **с одного взгляда**, без пояснений.
3. Продукт должен **выглядеть дороже, чем он есть по объёму функций** — за счёт аккуратности деталей, а не декоративности.
4. Каждое состояние (в том числе ошибки и заглушки) должно быть спроектировано осознанно — не отдано на откуп браузерным дефолтам.

---

## 3. Принципы дизайна

- **Лаконичность.** Минимум визуального шума; ни одного элемента, который не отвечает на вопрос пользователя «что происходит / что я могу сделать».
- **Аккуратность.** Выровненная сетка, консистентные отступы/иконки/состояния; ничего «на глаз».
- **Практичность.** Форма всегда следует за функцией конкретного сценария (звонок вчетвером в браузере), не за трендом ради тренда.
- **Продуманность в деталях.** Референс — эстетика современных agentic-интерфейсов (Claude, Hermes и подобные): простой на первый взгляд визуальный язык, но с проработанными микро-моментами (загрузка, переходы состояний), которые создают ощущение качества. См. раздел 7 — это WHAT, конкретные HOW сознательно не фиксируются здесь.
- **Референс по UX-тону** — рабочее демо `https://chat.forasoft.com` (используется как отправная точка ощущения, не как техническое или визуальное ТЗ).

---

## 4. Роли участников

Все участники **равноправны** — нет роли «модератор»/«создатель комнаты» с особыми правами (см. F-32 техн. PRD). Дизайн не должен визуально выделять создателя комнаты особым статусом/бейджем.

## 6. Пользовательские флоу

> Основные (частые) флоу — подробно, по шагам, с указанием экрана/состояния на каждом шаге. Технические детали (WebRTC/Socket.io) не упоминаются — только то, что видит и делает пользователь.

### Флоу A — Создание комнаты (инициатор)
1. **Стартовый экран** → поле «Ваше имя» + кнопка «Создать комнату».
2. Ввод имени (валидация в реальном времени: пусто / только пробелы / >30 символов / спецсимволы — см. каталог состояний, §8).
3. Нажатие «Создать комнату» → мгновенный переход в **экран комнаты**; пользователь — единственный участник.
4. Явное, заметное действие «Скопировать ссылку-приглашение» с понятным подтверждением копирования.

### Флоу B — Вход по ссылке (приглашённый участник)
1. Открытие ссылки-приглашения → **экран ввода имени** (та же валидация, что и в флоу A).
2. Подтверждение входа → подключение к **существующей** комнате (или к новой, если она уже опустела/удалена — для пользователя это неразличимо и не должно так выглядеть, см. F-05 техн. PRD).
3. Появление в видео-сетке рядом с уже присутствующими участниками; входящий получает системное уведомление в чате о своём же присоединении не показывается, но остальные видят «участник присоединился».

### Флоу C — Видео, аудио и управление медиа
1. При входе браузер запрашивает доступ к камере/микрофону — экран должен явно подготовить пользователя к этому системному диалогу, а не просто «подвиснуть» в ожидании.
2. По умолчанию микрофон и камера включены; собственное видео (self-view) визуально отличимо от остальных плиток.
3. Переключение микрофона/камеры — один клик, с однозначной обратной связью на своей же плитке и мгновенным отражением статуса на плитках у остальных.
4. Выключенная/недоступная камера → заглушка: силуэт + имя участника (не пустой чёрный прямоугольник).

### Флоу D — Чат и список участников
1. Чат/список участников — доступны из экрана комнаты, не мешая видео-сетке (панель или оверлей — решение экрана, не фиксируется здесь).
2. Отправка сообщения → мгновенное появление у всех, автопрокрутка вниз.
3. Системные события (вход/выход участника) — визуально отличимы от обычных сообщений (не выглядят как реплика человека).
4. Поздний вход: участник видит всю историю чата комнаты за время её жизни.

### Флоу E — Выход из комнаты
1. Явная кнопка «Выйти» — с однозначным, но не «пугающим» подтверждением (не деструктивная операция по сути, просто конец звонка).
2. После выхода — возврат на стартовый экран (ввод имени), не пустой/белый экран.
3. Закрытие вкладки эквивалентно выходу для остальных участников (без специального экрана — это фоновое поведение, не UI).

## 7. Моменты для проработки полировки (WHAT, без готового HOW)

Список мест, где стоит вложиться в деталь ради ощущения качества. Конкретные визуальные решения — предмет следующего шага (проработка референса), не фиксируются здесь:

- Ожидание/подключение к комнате сразу после входа (до появления первого видео).
- Появление и исчезновение плитки участника (вход/выход из комнаты).
- Переключение микрофона/камеры (визуальный отклик на своей и на чужих плитках).
- Подтверждение копирования ссылки-приглашения.
- Заглушка отсутствующего видео (силуэт + имя).
- Приход нового сообщения в чат / системного уведомления.
- Ожидание системного диалога о разрешении на камеру/микрофон.

## 8. Каталог экранов

| Экран | Назначение |
|---|---|
| Стартовый экран | Ввод имени, создание комнаты |
| Экран ввода имени по ссылке | Ввод имени перед входом в существующую комнату |
| Экран комнаты | Видео-сетка (1–4 плитки) + панель управления (микрофон/камера/выход) + чат/список участников |
| Заглушка видео участника | Силуэт + имя — при выключенной/отсутствующей/недоступной камере |

## 9. Каталог состояний и системных сообщений

> Компактно: что произошло → что должен увидеть/понять пользователь. Без сценариев Given/When/Then — это уже есть в техническом PRD (US-5, US-11–US-13).

| Состояние | Пользователь должен понять |
|---|---|
| Комната заполнена (5-й участник) | Понятное сообщение «Комната заполнена» + возможность повторить попытку |
| Пустое/некорректное имя | Подсказка, без входа в комнату |
| Отказ в доступе к камере/микрофону | Понятно, что доступа нет; пользователь остаётся в комнате с выключенными устройствами |
| Потеря устройства во время звонка | Понятно, что поток пропал; куда идти за исправлением (настройки браузера/ОС) |
| Обрыв соединения у другого участника | Его плитка исчезает, в чате — нейтральное системное сообщение о выходе (без формулировки «обрыв связи», см. техн. PRD US-11) |
| Сервер недоступен | Понятное сообщение об ошибке сервера, не «белый экран» |
| Браузер не поддерживает WebRTC | Явное сообщение о неподдерживаемом браузере |
| Заблокирован autoplay звука | Понятный призыв к действию, чтобы включить звук |

## 10. Ограничения (перенесены из технического PRD без изменений)

- **Только десктоп**, корректная адаптация от ширины **1024px**; мобильная адаптация вне скоупа.
- **Только русский язык** интерфейса, без i18n.
- **Без авторизации** — доступ к комнате не ограничивается идентификатором; в UI это не должно выглядеть как «незащищённость», а как осознанная простота сценария.
- **Нет привилегий создателя комнаты** — интерфейс не выделяет его особо (см. §4).
- Ничего не сохраняется на клиенте между перезагрузками (в т.ч. имя нужно будет ввести заново).

Полный список нефункциональных ограничений и non-goals — см. `prd-video-chat-room.md`, разделы 5 и 7.
