## 0. Источник истины и доступ агентов

Утверждённый дизайн живёт в облачном проекте Claude Design **«Видеочат: прототип и
состояния»** (`868b37de-9154-4622-81a1-91ab91811dfa`), файлы `design_handoff_video_chat_room/`.
Композиция экрана комнаты — **вариант 1c «Говорящий крупно»** (утверждена).

**Локальное зеркало.** Суб-агенты пайплайна (`design-architect`, `implementer`,
`code-reviewer` и т.д.) не имеют инструмента `DesignSync` — они не могут прочитать облачный
проект напрямую. Поэтому два файла (по фокусу этой сессии) синхронизированы в репозиторий:

```
prds/video-chat-room/design-handoff/
├── README.md                                          — полный hi-fi спек (источник значений)
└── prototypes/
    ├── Видеочат - экраны и состояния.dc.html           — канвас: 3 варианта композиции +
    │                                                     каталог состояний §9 + заглушки видео
    └── support.js                                       — рантайм просмотра (открыть .dc.html
                                                            в браузере рядом с этим файлом)
```

`prototypes/Видеочат - прототип.dc.html` (кликабельный флоу всех экранов) в зеркале **не
сохранён** — вне фокуса, который просил пользователь при снятии копии. При необходимости
пиксельной сверки конкретного перехода синхронизировать его тем же способом (`DesignSync
get_file` → извлечь `.content` → записать в `design-handoff/prototypes/`).

**Правило для агентов:** значения (HEX, px, cubic-bezier, копирайт) брать из
`design-handoff/README.md` или, если чего-то не хватает, из разметки `.dc.html` — **не
изобретать** и не приближать «на глаз». `README.md` явно требует pixel-perfect (раздел
Fidelity).

## 1. Статус на момент написания

Все 33 задачи `impl-video-chat-room.md` закрыты — функционал полный и покрыт тестами
(225 server + 267 client + 6 E2E). Но **ни одного CSS-файла в кодовой базе нет**: компоненты
рендерят структуру с семантичными `className`/`data-testid`, без единого стиля. Композиция
экрана комнаты — плоский вертикальный стек (`VideoGrid` → `ControlBar` → `ParticipantList` →
`ChatPanel`), не совпадающий по структуре с утверждённой «1c» (сцена + лента + сворачиваемая
панель с табами).

Эта визуальная реализация — не косметика поверх готового макета, а частично ещё и
**реструктуризация компоновки** экрана комнаты. Gap-анализ — §3.

## 2. Архитектура стилизации (зафиксировано)

- **CSS Modules**, без новых npm-зависимостей — Vite поддерживает `*.module.css` из коробки.
  Файл стилей лежит рядом с компонентом: `ComponentName.jsx` + `ComponentName.module.css`,
  импорт `import styles from './ComponentName.module.css'`, классы через `styles.xxx`.
- **Design-токены** — один файл `app/client/src/styles/tokens.css`, CSS custom properties
  на `:root`, имена = токены из `design-handoff/README.md` → Design Tokens (`--ink: #14130F`,
  `--bg: #EFEDE8`, `--line: #E2DED5`, …), плюс отступы/радиусы как отдельные переменные
  (`--space-4` … `--space-44`, `--radius-8` … `--radius-999`). Импортируется один раз в
  `app/client/src/main.jsx`. Модульные CSS-файлы читают их через `var(--ink)` — не хардкодят
  HEX повторно.
- **Шрифты** — `<link>` на Google Fonts (Golos Text, JetBrains Mono, Workbench) в
  `app/client/index.html`, как в прототипе. Не npm-пакет шрифта.
- **Иконки** — инлайновый SVG 24×24 прямо в JSX компонентов (как в прототипе), не
  icon-библиотека. `stroke-width`/`stroke-linecap`/`currentColor` — по прототипу.
- Ничего из этого не требует правок `package.json`/`package-lock.json` — согласуется с
  TDD §10.5 SEC-19 («минимум прод-зависимостей»), уже зафиксированным для этого проекта.
- Тема — **одна**, светлая, без переключателя (закрывает вопрос §5 `prd-ux-video-chat-room.md`,
  см. пометку SUPERSEDED в этом файле).

## 4. Что менять нельзя (инварианты этого захода)

Визуальная реализация не должна тронуть уже проверенные security- и архитектурные гарантии:

- **SEC-04** (`design-video-chat-room.md` §10.1) — имя участника, текст сообщения, любой
  пользовательский контент по-прежнему рендерится **только** текстовым узлом React
  (`{value}`), включая новые места (чипы имени на сцене/ленте, табы, тултипы).
  `dangerouslySetInnerHTML` запрещён линтером — не отключать правило ради вёрстки.
- **SEC-14** (roomId) — `roomId` в URL остаётся полным `crypto.randomUUID()` (§6.4 TDD).
  «Код комнаты» вида `RM-4F2A` в шапке — **чисто косметическое** форматирование для
  отображения, не новая схема идентификаторов и не то, что уходит на сервер как ключ
  поиска. См. развилку §5.2 ниже.
- **SEC-19** — ноль новых прод-зависимостей (см. §2: CSS Modules/Google Fonts/inline SVG —
  всё либо встроено в Vite, либо не требует `npm install`).
- Только десктоп, минимальная ширина **1024px**, без адаптации под мобильные — ограничение
  не снимается, дизайн сам заявляет то же самое.
- Одна тема без переключателя (§2 выше) — не добавлять toggle «на всякий случай».
- Существующие `data-testid`, на которые опираются 267 client-тестов и 6 E2E-сценариев, —
  при реструктуризации (§3, статус RESTRUCTURE/NEW) их можно переименовывать/перемещать, но
  **только вместе** с обновлением соответствующего тест-файла в том же PR, не молча.
- WebRTC/mesh/signaling-логика (`webrtc/`, `hooks/useSignaling.js`, `hooks/useMesh.js`,
  `services/*` на сервере) — вне скоупа; это чисто UI-слой поверх уже работающего транспорта.

## 5. Развилки, которые пришлось решить (и как)

Дизайн вводит несколько элементов, которых не было в исходном техническом PRD/TDD. Ниже —
принятые решения с обоснованием; при несогласии — это единственное место, где стоит спорить,
не в отдельных задачах реализации.

### 5.1 «Активный говорящий» (`activeSpeakerId`) — без реального VAD
Дизайн вводит понятие «сцена = активный участник», которого не было в исходном F-07
(«адаптивная сетка 1–4 плитки», без выделения кого-то одного). `design-handoff/README.md`
сам описывает мягкий fallback: `activeSpeakerId // кто на сцене: говорящий, иначе первый
другой, иначе вы` — то есть реальное определение речи (voice-activity detection) не
обязательно для корректной раскладки.

**Решение:** в этом заходе — эвристика без анализа громкости (первый участник кроме себя,
иначе сам себя; смена — при join/leave). Настоящий VAD (Web Audio API `AnalyserNode` на
каждый remote-поток; браузерное API, не требует новой npm-зависимости, но добавляет новую
клиентскую логику без протокольной поддержки на сервере — `media:state` сейчас несёт только
`{audio, video}`, не громкость) — сознательно вне объёма: не требовался ни техническим PRD,
ни исходной TDD, его отсутствие не блокирует утверждённую раскладку «сцена + лента».
Эквалайзер-индикатор «ГОВОРИТ» из дизайна в этом заходе не подключается к реальному звуку —
если продукту важен настоящий VAD, это отдельная задача вне этого плана (по прецеденту
«задача 12 закрыта решением пользователя» в `checklist.md` — в проекте уже есть практика
явно фиксировать такие сознательные сокращения объёма).

> **Вернуться к этому позже.** Пользователь явно попросил зафиксировать намерение вернуться
> к «фишкам», которые есть в утверждённом дизайне, но сознательно не вошли в задачи 34–44 —
> в первую очередь настоящий VAD/`speaking`-индикатор (эта развилка). Если появится
> возможность/приоритет — заводить как отдельную задачу (после 44, с собственным протокольным
> решением: как минимум client-side `AnalyserNode` на remote-поток + троттлинг обновлений
> `activeSpeakerId`, без изменений в `media:state` сервера, если громкость не нужно
> синхронизировать между пирами).

### 5.2 «Код комнаты» в шапке (`RM-4F2A`) — косметика, не новый ID
См. инвариант §4 SEC-14. **Решение:** чистая функция форматирования на клиенте
(`formatRoomCode(roomId)` — например, первые 4 символа UUID без дефисов, в верхнем регистре,
с префиксом `RM-`), используется **только** для отображения в шапке; `roomId` в URL/
`join`-payload/сравнениях не меняется. Коллизия отображаемого кода у двух разных комнат
возможна и допустима — это не идентификатор, а декоративная деталь (аналог «номера стола»).

### 5.3 Таймер звонка (`MM:SS`)
Новое состояние, не было в §5.3 TDD. **Решение:** чисто клиентское, `RoomScreen`, тик раз в
секунду от момента успешного `join:ok` (`Date.now()` на старте + `setInterval`/`useEffect`).
Не требует изменений протокола/сервера.

### 5.4 Слияние чата и списка участников в табы
Дизайн (§5) — одна сворачиваемая панель с переключателем «Чат / Участники» и общим счётчиком
непрочитанных, а не два всегда видимых блока, как сейчас. **Решение:** `ParticipantList.jsx`
переиспользуется как содержимое вкладки «Участники» внутри новой сворачиваемой панели
(контейнер с табами и анимацией ширины — новый компонент, см. задачу в §7); `unread` — новое
состояние в `RoomScreen`, инкремент на `onChatMessage`/`onChatSystem` пока панель закрыта или
открыта не на вкладке «Чат», сброс при открытии на неё.

## 6. Тестирование и приёмка

- Ни одна из задач §7 не помечена `critical` в смысле `rules/prd-tasks.mdc` — новых
  security-/data-integrity-инвариантов не вводится (SEC-04/SEC-14 не меняются, только
  соблюдаются — см. §4). Гейт «тесты до кода» на них не распространяется.
- Но обычный гейт проекта «код написан, тесты зелёные» — распространяется. Тесты пишутся на
  **поведение и структуру**, не на пиксели: RTL/jsdom не умеет content-фул проверять
  вычисленный CSS. Что стоит покрывать тестами: `activeSpeakerId`-эвристику (join/leave меняют
  выбор), инкремент/сброс `unread`, гейт «Выйти» → модалка → только затем `leave`, форматтер
  `formatRoomCode` (частая цель регрессии — легко случайно завязать на реальный roomId),
  таймер (fake timers), появление/скрытие тоста копирования по таймауту.
- Визуальную точность (цвета/отступы/шрифты/motion) проверяет **человек в браузере** —
  запустить `npm run dev`, сверить с `design-handoff/prototypes/Видеочат - экраны и
  состояния.dc.html` (открыть напрямую в браузере) и/или с прототипом в облачном Claude
  Design проекте, до отчёта о готовности задачи (это уже требование глобальных инструкций
  проекта для UI-задач, тут явно применяется).
- Реструктуризация (статус RESTRUCTURE/NEW в §3) может потребовать переименования/переноса
  `data-testid` — при этом обязательный прогон **всей** существующей клиентской сюиты
  (267 тестов) + E2E (6 сценариев), не только новых тестов задачи, и обновление задетых
  существующих тест-файлов в том же PR (см. инвариант §4).
