# Fora Soft — Проектные инструкции

## Что это за проект
Разработка ведётся по **спецификационному пайплайну** (spec-driven development).
Любая фича проходит через фиксированные стадии, каждая оформляется отдельным
документом. Код пишется только после того, как готовы дизайн и план.

## Пайплайн фичи

```
(разово)  Security baseline ─┐
                             ▼
PRD ─► TDD ─► Plan ─► [тесты(крит.) ─► код] ─► Ревью ─► (Security-аудит) ─► PR
```

| Стадия | Агент | Команда | Вход / правила | Выход |
| ------ | ----- | ------- | -------------- | ----- |
| Security-baseline (разово) | `security-auditor` | `/threat-model` | PRD | `security/security-baseline.md` |
| Дизайн | `design-architect` | `/design` | `rules/prd-design.mdc` + baseline | `prds/<feature>/design-<feature>.md` |
| План   | `task-planner`     | `/plan`   | `rules/prd-tasks.mdc` | `prds/<feature>/impl-<feature>.md` |
| Тесты (крит.) | `test-author` | `/test` | TDD §11 + критерии приёмки | падающие тесты |
| Реализация | `implementer`  | `/implement` | план + TDD | код (тесты зелёные), **локальный коммит, без push/PR** |
| Ревью  | `code-reviewer`    | —         | TDD + требования | список замечаний (PASS → чеклист) |
| Security-аудит (если нужен) | `security-auditor` | `/security-audit` | baseline + TDD §10 | находки |
| PR | — | — | Ревью PASS (+ Security-аудит, если требовался) | PR в `develop` |

**PR — последний шаг, не промежуточный.** Ветка живёт и коммитится локально,
пока код-ревью (и, если применимо, security-аудит) не пройдены; `git push` /
`gh pr create` выполняются только после этого. Причина: PR должен появляться
уже провалидированным, а не служить площадкой для самого ревью через GitHub.

## Правила именования `feature-name`
- `kebab-case`, латиница, `-` — разделитель, ≤ 50 символов.
- Пробелы и спецсимволы убирать: «Импорт профиля» → `import-profile`.
- Все артефакты фичи лежат в одной папке: `prds/<feature-name>/`.
- Версионирование доработок: `design-<feature>-v2.md`, `impl-<feature>-v3.md`, …

## Git-флоу и Pull Requests
- Работаем по **Git Flow**: `main` (релизы) ← `develop` (интеграция) ←
  `feature/*`; при необходимости `release/*` и `hotfix/*`.
- Ветка под задачу: `feature/<feature-name>-<task-id>` (напр. `feature/video-chat-room-1.2`).
- **Один PR = одна задача плана.** PR открывается в `develop`.
- Коммиты и PR ссылаются на пункт плана; PR заполняется по шаблону
  `.github/pull_request_template.md`.
- **PR открывается только ПОСЛЕ успешного локального `code-reviewer`** (и
  `security-auditor`, если он нужен для этой задачи — обязателен для мержа
  эпика в `main`, рекомендован для отдельной `critical: YES` задачи). До
  этого момента `implementer` только коммитит в feature-ветку **локально** —
  без `git push` и без `gh pr create`. Ревью проходит код *до* того, как он
  покидает локальную ветку, а не через ревью уже открытого GitHub PR.
- Мерж задачи в `develop` — после `code-reviewer`; ручной `security-auditor`
  для отдельной задачи опционален (рекомендован для `critical: YES`), не
  блокируется хуком. Хук блокирует только мерж эпика в `main` (релиз/hotfix)
  без пройденного security-аудита — см. «Живой чеклист и гейты».
- **GitHub-настройки** (защита веток, auto-merge, CI, стратегия мержа) описаны
  в `.github/README.md`. `develop`/`main` защищены: только PR, зелёный CI
  (`hygiene`), запрет force-push/удаления; merge-коммиты; auto-merge по зелёному.

## Живой чеклист и гейты (защита от «человеческого фактора»)
На каждую фичу `task-planner` генерирует `prds/<feature>/checklist.md` из
`.claude/templates/feature-checklist.md`. Это **источник правды о прогрессе**:
каждый агент, начиная шаг, читает чеклист, сверяется с гейтами и обновляет его.
Задача любого агента — напоминать пользователю о пропущенном.

**Компактные записи.** Отметка в чеклисте — одна строка (факт + при
необходимости ссылка на PR/коммит/маркер), не абзац-нарратив. Детали и так
есть в самом PR/коммите/отчёте агента.

Два блокирующих гейта (⛔):
1. **Test-first перед кодом.** Для `critical: YES` `implementer` в preflight
   проверяет: тесты написаны и по ним дан отчёт, и пользователь **явно** дал
   команду на реализацию. Нет — код не пишется, агент напоминает и ждёт.
2. **Security review перед вливанием эпика в `main`.** Гейт привязан к
   **эпику (релизу), не к каждому PR задачи** — рядовые задачи фичи вливаются
   в `develop` без аудита. Обеспечивается **хуком** `.claude/hooks/pre-merge-gate.js`
   (зарегистрирован в `.claude/settings.json`): он реагирует только на
   `gh pr create --base main`/`master`, `git merge`/`push`, когда цель —
   `main`/`master` (release/hotfix). PR/push отдельной задачи фичи в `develop`
   хуком **не блокируется**. Вливание в `main`/`master` блокируется, пока для
   текущего коммита не появится маркер `.gates/security-<short-HEAD>.ok`.
   Маркер получают:
   - **Ручной `/security-audit`** (`security-auditor`) — обязателен перед
     мержем эпика в `main`. Для отдельной задачи `critical: YES` в `develop`
     он рекомендован, но не enforced хуком — по дисциплине/чеклисту. Аудит
     **скопирован на дифф до базы релиза** — полный пересмотр baseline
     делается один раз на `/threat-model`, не переигрывается на каждой задаче.
   - **`node scripts/security-gate.js`** — авто-гейт: если дифф до `main` не
     трогает по-настоящему чувствительные пути (секреты, auth/crypto/session/
     rate-limit код, сокет-слой, CI workflows, сам гейт — см. список в
     `scripts/security-gate.js`), сам прогоняет `npm test`/`lint`/`audit` и
     при зелёном результате сам ставит маркер, без вызова агента.
   - **Rebind (авто, без действий агента).** Если изменённый файл в диффе
     побайтово совпадает с версией, уже аудированной ранее (хук сверяет
     `git hash-object` с записями в `.gates/security-*.files`, которые пишут оба
     пути выше), повторный аудит по этому файлу не нужен — хук пропускает его
     сам.
   **Исключение (doc-only):** если вливаемый в `main` дифф состоит *только*
   из документации (`.md`, `.mdc`, `.markdown`, `LICENSE`, `NOTICE`,
   `.gitignore`, `.gitattributes`, `.editorconfig`), аудит не требуется. Если
   дифф вычислить не удалось — fail-safe: блокируется до ручного `/security-audit`.

## Формат отчётов агентов
Любой отчёт — в чат, в чеклист, или от суб-агента вызвавшему его агенту —
**2–4 строки**: что сделано + проблемы/блокеры (если есть) + ссылка
(PR/коммит/файл). Без пересказа процесса, содержимого файлов или диффа — это
уже видно в самих артефактах. Исключение — списки находок ревью/аудита
(`code-reviewer`, `security-auditor`): там объём равен числу находок, а не
тексту вокруг них.

## Test-first для критичного функционала
- Критичные задачи (безопасность, деньги, целостность данных, ключевые
  инварианты) плановик помечает `[critical]` и делит на «тесты» → «код».
- Тесты пишет `test-author` **до** реализации; они должны падать (red);
  затем он отчитывается и **ждёт команды** пользователя (гейт в чеклисте).
- `implementer` делает их зелёными и **не меняет** сами тесты.

## Безопасность
- До старта разработки — разовый `security/security-baseline.md` (модель угроз
  STRIDE + чек-лист требований), командой `/threat-model`.
- Каждый TDD в разделе 10 опирается на baseline.
- Перед мержем **эпика (релиза)** в `main` — обязательный `/security-audit`
  (аудит по baseline и §10 TDD, **скоуп — дифф до `main`**, не вся кодовая база
  заново). Отдельные задачи фичи вливаются в `develop` без обязательного
  аудита; для `critical: YES` он рекомендован перед собственным PR задачи, но
  не блокирует его. См. «Живой чеклист и гейты» выше.

## Архитектура фронтенда: без хардкода, компонент — кирпичик
Действует для всех компонентов `app/client/src` (не только для дизайн-токенов).

- **Единый источник для любого «магического» значения.** Уже зафиксировано
  для цветов/отступов/радиусов/шрифтов — `app/client/src/styles/tokens.css`
  (`design-ui-video-chat-room.md` §2): компонент не хардкодит HEX/px
  повторно, а берёт `var(--token)`. Тот же принцип действует и для
  **пользовательского текста/копирайта**: заголовки, подписи, тексты
  подсказок/ошибок, плейсхолдеры — не литералом посреди JSX компонента, а
  вынесены в отдельный модуль контента рядом с компонентом (например,
  `ScreenName.content.js`), компонент импортирует их оттуда.
- **Компонент — кирпичик, не монолит.** Контент и специфика конкретного
  экрана передаются через `props`/конфиг, а не зашиваются намертво внутрь
  компонента. Компонент должен оставаться пригодным для повторного
  использования/замены содержимого без правки его собственного кода.
- **Зачем.** Сейчас интерфейс — только русский (`design-handoff/README.md` →
  Layout constants), но архитектура не должна закрывать дорогу к
  локализации или замене копирайта в будущем: если контент разбросан
  литералами по компонентам, любое такое изменение превращается в поиск по
  всей кодовой базе вместо правки одного файла.
- **Проверяется на `code-reviewer`.** Хардкод текста/значения без единого
  источника — замечание (major/minor по масштабу дублирования), которое
  нужно закрыть до мержа задачи в `develop`, наравне с остальными
  находками ревью.

## Где что лежит
- `rules/prd-design.mdc` — правила составления Technical Design Document.
- `rules/prd-tasks.mdc` — правила составления Implementation Plan.
- `prds/<feature>/prd-<feature>.md` — PRD фичи (первая: `video-chat-room`).
- `prds/<feature>/` — все артефакты фичи: PRD, дизайн, план.
- `.claude/commands/graphify.md` — запуск `graphify` для построения графа связей по текущему workspace.
- `security/security-baseline.md` — продуктовая модель угроз и чек-лист.
- `.github/pull_request_template.md` — шаблон PR.
- `.claude/agents/` — специализированные агенты стадий.
- `.claude/commands/` — слэш-команды для запуска стадий.
- `scripts/security-gate.js` — авто-гейт перед мержем эпика в `main` для
  диффов без чувствительных путей (см. «Живой чеклист и гейты»).

## Ключевые принципы
1. **Не перескакивать стадии.** Нет TDD — не пишем план; нет плана — не пишем код.
2. **Дизайн-агент не пишет production-код** — только проектирует.
3. **Одна задача плана = один MR/PR** (0.25–1 день работы).
4. Каждый артефакт ссылается на предыдущий: TDD → на ID требований PRD,
   план → на ID требований и разделы TDD, код/коммит → на пункт плана.
5. Если данных не хватает — задать уточняющие вопросы, а не додумывать.
6. **Безопасность и тесты — не постскриптум:** baseline до дизайна,
   тесты до кода на критичном, аудит до мержа.
7. **Фронтенд без хардкода.** Текст и «магические» значения — из единого
   источника (токены/контент-модуль), не литералом внутри компонента; см.
   «Архитектура фронтенда: без хардкода, компонент — кирпичик» выше.
