# Fora Soft — Проектные инструкции

## Что это за проект
Разработка ведётся по **спецификационному пайплайну** (spec-driven development).
Любая фича проходит через фиксированные стадии, каждая оформляется отдельным
документом. Код пишется только после того, как готовы дизайн и план.

## Пайплайн фичи

```
(разово)  Security baseline ─┐
                             ▼
PRD ─► TDD ─► Plan ─► [тесты(крит.) ─► код] ─► Ревью + Security-аудит
```

| Стадия | Агент | Команда | Вход / правила | Выход |
| ------ | ----- | ------- | -------------- | ----- |
| Security-baseline (разово) | `security-auditor` | `/threat-model` | PRD | `security/security-baseline.md` |
| Дизайн | `design-architect` | `/design` | `rules/prd-design.mdc` + baseline | `prds/<feature>/design-<feature>.md` |
| План   | `task-planner`     | `/plan`   | `rules/prd-tasks.mdc` | `prds/<feature>/impl-<feature>.md` |
| Тесты (крит.) | `test-author` | `/test` | TDD §11 + критерии приёмки | падающие тесты |
| Реализация | `implementer`  | `/implement` | план + TDD | код (тесты зелёные), PR |
| Ревью  | `code-reviewer`    | —         | TDD + требования | список замечаний |
| Security-аудит | `security-auditor` | `/security-audit` | baseline + TDD §10 | находки |

## Правила именования `feature-name`
- `kebab-case`, латиница, `-` — разделитель, ≤ 50 символов.
- Пробелы и спецсимволы убирать: «Импорт профиля» → `import-profile`.
- Все артефакты фичи лежат в одной папке: `prds/<feature-name>/`.
- Версионирование доработок: `design-<feature>-v2.md`, `impl-<feature>-v3.md`, …

## Git-флоу и Pull Requests
- Работаем по **Git Flow**: `main` (релизы) ← `develop` (интеграция) ←
  `feature/*`; при необходимости `release/*` и `hotfix/*`.
- Ветка под задачу: `feature/<feature-name>-<task-id>` (напр. `feature/video-chat-room-1.2`).
- **Один PR = одна задача плана.** PR открывается в `develop`.
- Коммиты и PR ссылаются на пункт плана; PR заполняется по шаблону
  `.github/pull_request_template.md`.
- Мерж только после `code-reviewer`, а для критичного — ещё и `security-auditor`.
- **GitHub-настройки** (защита веток, auto-merge, CI, стратегия мержа) описаны
  в `.github/README.md`. `develop`/`main` защищены: только PR, зелёный CI
  (`hygiene`), запрет force-push/удаления; merge-коммиты; auto-merge по зелёному.

## Живой чеклист и гейты (защита от «человеческого фактора»)
На каждую фичу `task-planner` генерирует `prds/<feature>/checklist.md` из
`.claude/templates/feature-checklist.md`. Это **источник правды о прогрессе**:
каждый агент, начиная шаг, читает чеклист, сверяется с гейтами и обновляет его.
Задача любого агента — напоминать пользователю о пропущенном.

**Компактные записи.** Отметка в чеклисте — одна строка (факт + при
необходимости ссылка на PR/коммит/маркер), не абзац-нарратив. Детали и так
есть в самом PR/коммите/отчёте агента.

Два блокирующих гейта (⛔):
1. **Test-first перед кодом.** Для `critical: YES` `implementer` в preflight
   проверяет: тесты написаны и по ним дан отчёт, и пользователь **явно** дал
   команду на реализацию. Нет — код не пишется, агент напоминает и ждёт.
2. **Security review перед вливанием.** Обязателен перед `gh pr create` / push /
   merge в `develop`/`main`. Обеспечивается **хуком** `.claude/hooks/pre-merge-gate.js`
   (зарегистрирован в `.claude/settings.json`): действие блокируется, пока для
   текущего коммита не появится маркер `.gates/security-<short-HEAD>.ok`. Новый
   коммит с реально новым содержимым → нужен повторный проход одного из путей
   ниже. Гейт **риск-тиированный**, не поголовный — маркер можно получить тремя
   способами:
   - **Ручной `/security-audit`** (`security-auditor`) — обязателен для
     `critical: YES` и для диффов, трогающих чувствительные пути (`.claude/**`,
     `.github/workflows/**`, `security/**`, `app/server/src/socket/**`,
     `config.js`, `validate.js`/`sanitize.js`, `package.json`/lockfiles,
     `Dockerfile*`/`docker-compose*`, `.env*`, файлы с auth/token/session/crypto/
     rate-limit в имени). Сам ручной аудит **скопирован на дифф**: проверяются
     изменённые файлы и то, что они напрямую затрагивают, а не вся кодовая база
     заново на каждую задачу — полный пересмотр baseline делается один раз на
     `/threat-model`, не переигрывается на каждом PR.
   - **`node scripts/security-gate.js`** — авто-гейт для `critical: NO` без
     чувствительных путей: сам прогоняет `npm test`/`lint`/`audit` и при зелёном
     результате сам ставит маркер, без вызова агента.
   - **Rebind (авто, без действий агента).** Если изменённый файл в диффе
     побайтово совпадает с версией, уже аудированной ранее (хук сверяет
     `git hash-object` с записями в `.gates/security-*.files`, которые пишут оба
     пути выше), повторный аудит по этому файлу не нужен — хук пропускает его
     сам. Действует «через ветки», пока содержимое не менялось.
   **Исключение (doc-only):** если вливаемый дифф (`<base>...HEAD`) состоит
   *только* из документации (`.md`, `.mdc`, `.markdown`, `LICENSE`, `NOTICE`,
   `.gitignore`, `.gitattributes`, `.editorconfig`), аудит не требуется — гейт
   пропускает автоматически. `.txt` в это исключение намеренно НЕ входит (может
   маскировать манифест зависимостей вроде `requirements.txt`). Стоит хоть один
   файл кода/конфига/зависимостей — нужен один из трёх путей выше (исключение
   контентное, не по намерению: код-«фиксы» тоже аудируются). Если дифф
   вычислить не удалось — fail-safe: исключения не применяются, действие
   блокируется до ручного `/security-audit`.

## Test-first для критичного функционала
- Критичные задачи (безопасность, деньги, целостность данных, ключевые
  инварианты) плановик помечает `[critical]` и делит на «тесты» → «код».
- Тесты пишет `test-author` **до** реализации; они должны падать (red);
  затем он отчитывается и **ждёт команды** пользователя (гейт в чеклисте).
- `implementer` делает их зелёными и **не меняет** сами тесты.

## Безопасность
- До старта разработки — разовый `security/security-baseline.md` (модель угроз
  STRIDE + чек-лист требований), командой `/threat-model`.
- Каждый TDD в разделе 10 опирается на baseline; каждый PR сверяется с ним.
- Перед мержем критичного или чувствительного по путям — `/security-audit`
  (аудит по baseline и §10 TDD, **скоуп — дифф**, не вся кодовая база заново).
  Для остального — риск-тиированный гейт, см. «Живой чеклист и гейты» выше.

## Где что лежит
- `rules/prd-design.mdc` — правила составления Technical Design Document.
- `rules/prd-tasks.mdc` — правила составления Implementation Plan.
- `prds/<feature>/prd-<feature>.md` — PRD фичи (первая: `video-chat-room`).
- `prds/<feature>/` — все артефакты фичи: PRD, дизайн, план.
- `security/security-baseline.md` — продуктовая модель угроз и чек-лист.
- `.github/pull_request_template.md` — шаблон PR.
- `.claude/agents/` — специализированные агенты стадий.
- `.claude/commands/` — слэш-команды для запуска стадий.
- `scripts/security-gate.js` — авто-гейт для некритичных задач без
  чувствительных путей (см. «Живой чеклист и гейты»).

## Ключевые принципы
1. **Не перескакивать стадии.** Нет TDD — не пишем план; нет плана — не пишем код.
2. **Дизайн-агент не пишет production-код** — только проектирует.
3. **Одна задача плана = один MR/PR** (0.25–1 день работы).
4. Каждый артефакт ссылается на предыдущий: TDD → на ID требований PRD,
   план → на ID требований и разделы TDD, код/коммит → на пункт плана.
5. Если данных не хватает — задать уточняющие вопросы, а не додумывать.
6. **Безопасность и тесты — не постскриптум:** baseline до дизайна,
   тесты до кода на критичном, аудит до мержа.
